# Restoration after a Board A USB dropout

When a drive helper cannot verify restoration, its wildcard inhibit protects **every** channel. The broker also remembers the failure in memory. Do not end an inhibit to get telemetry back without establishing why it was written. `--enable-usb-drop-recovery` is a narrow, off-by-default exception: the broker that saw the grant, armed status and failed restoration can verify replacement devices and end its own records. There is no automatic USB reset, diagnostic transmission, routine resumption or helper launch in this transaction. Normal helper admission still requires new qualifying evidence.

## What the evidence establishes

The collector has 900 seconds from the first latch. Its C-CAN helper must have latched; B-CAN alone does not qualify. For each latched helper it must have the same Board A kernel instance before the grant and after arming. Those ifindexes must be gone from a complete netdev inventory. Both current roles must resolve by serial and controller number to a *different USB enumeration* of Board A, with both replacement links positively DOWN. A rename, a reset with the same USB device number, missed packets, a USB monitor event or a successful read by itself is not enough. USB monitor IDs in the record are correlation only.

The broker refuses if a radar service-alignment run was requested during the C-CAN launch, was active at its claim or is active now, or if this history is uncertain. It waits for both claims and the auxiliary thread to finish, no hold, no unrecorded startup fault, a quiet broker service cgroup, and no foreign same-boot inhibit. An unverifiable cgroup, a missing or altered owned record, or a boot/time mismatch cannot authorize a recovery. Nonparticipating processes outside the service are not ruled out by these checks.

The collector pauses both display observers and locks all roles in order: C-CAN and B-CAN exclusively, CAN CH and spare shared. It resolves and locks the current Board A channel names exclusively, then repeats its checks. Shared Board B observers may continue. No Board B channel is configured. Before configuring anything it spends **one attempt per boot**, including unsuccessful attempts: the exclusive-create reservation is file- and directory-synced. The broker never resumes an incident opened by another process.

Before it pauses a display or takes a lock, the collector checks that `/home/pi/hooks/ignition_is_on` is a regular file. It checks again under the locks before spending the attempt. Missing, wrong-type or inaccessible means `waiting/ignition_not_on` until the window expires. The producer is `ignitionmon.service` (`/home/pi/scripts/ignition_monitor.sh`, MacBook-managed). Its Wi-Fi scans detect an ignition-associated network; the script creates the marker on a positive scan and removes it after three negative scans. That is a scan count, not a time limit. **A present marker is never engine evidence.** Key-on without the engine running can set it; a stopped or stalled monitor can leave its last positive marker indefinitely. There is no live service probe or age check. If the monitor stops with the marker absent, recovery cannot fire. If it stops with the marker present, the ordinary C-CAN bootstrap can still spend the attempt: a silent bus fails identity (`wrong_bus`); a recognizable bus without running RPM fails `engine_not_running`. Neither case ends an inhibit or commands B-CAN.

First it starts C-CAN in classical listen-only mode. One kernel request addresses the numeric ifindex directly (no name or alternative name), setting bit timing and passive flags together with UP. Fresh readback must match the expected instance, bitrate, listen-only, FD off, one-shot off, restart-ms 0 and ERROR-ACTIVE. The collector passively identifies C-CAN and requires three fresh RPM samples at or above 400. Only then does it configure and verify B-CAN the same way and refresh both topology records. After rechecking gates, processes, inhibits and both passive links, it samples running RPM again. Every unlink completes within 2 s of the start of a read that showed the engine running, or is undone. If no record remains removed, an expired deadline permits one fresh sample and retry. If the undo itself fails, recovery keeps every latch and reports `committed_late` for inspection; it does not claim the timing guarantee was met.

**Bootstrap and accepted physical limit.** The engine cannot be proven running with Board A DOWN. Even if the engine is off, an attempt can therefore bring C-CAN up listen-only for about two seconds and spend the boot's budget. Usually it then returns DOWN; after a crash or unverifiable rollback it can remain UP with inhibits in place until inspected. Enabling this bootstrap requires the owner's explicit acceptance. The owner accepted the separate unbenchmarked firmware risk: a new kernel netdev, a changed USB devnum and host listen-only readback do not physically prove an already-powered controller stopped transmitting across a disconnect. The consequence is lower while driving, when diagnostics already use a transmit-capable adapter at the right bitrate; when parked, a stuck controller can keep modules awake and drain the battery.

## Commit, refusal and crash recovery

The expected owned names, in order, are `vehicle-data-restoration-failed` and, only if its helper latched, `vehicle-data-bcan-restoration-failed`. The end operation compares *all* same-boot records to the exact expected payloads under the inhibit writer lock, checks the clock before and after each unlink and syncs the directory after each. If an unlink finishes late, the same writer restores the identical payload to its canonical path under the lock before releasing it. A concurrent writer unable to obtain the lock publishes a distinct wildcard `nolock.<boot>.<name-hash>`; its `stands_for` identifies the logical name. Both current and older readers honour the wildcard. No conditional end removes a fallback. A late fallback survives even if it arrives during a commit.

With no record left removed, failure means leave every inhibit and latch in place and attempt rollback for every possibly effective mutation, including one that timed out. A preflight refusal is `not_submitted`: rollback never takes down a link recovery did not attempt to bring up. A confirmed kernel rejection likewise needs no rollback. A quiet cgroup must be positively established before trusting rollback: a root submitter can outlive its `sudo` process. A replacement whose DOWN state or disappearance cannot be proved is `rollback_unverified`; inspect it. After any removal that was not undone there is **no rollback**: the links were verified passive at the commit. A partial commit leaves both in-memory latches; a remaining wildcard protects every channel. Only a complete, on-time commit clears the incident's in-memory latches. A directory-sync failure after unlink is recorded; power loss could restore the inhibit, which is conservative. A crash before reservation leaves the old wildcards for a person. A crash after reservation leaves that budget spent, with zero, one or both replacement links possibly UP listen-only. A crash after the first unlink leaves the second wildcard; after the last unlink a restart follows ordinary startup assessment.

`journalctl -u van-telemetry` reports transitions. The incident JSON files and `reservation-<boot_id>.json` are under `tmp/vehicle_data/usb-recovery/`; they are audit evidence, not recovery instructions. The vocabulary and exact limits live in `usb_recovery_contract.py`: `open` and `waiting` precede `reserved`, `configuring`, `verifying`, `committing`. Terminal states include `ineligible`, `failed`, `committed`, `partial_commit`, `committed_late`, `committed_latches_kept` and `commit_outcome_unknown`. Inspect the state's `reason`, submitted mutations, rollback outcomes, actual ended names and durability. At most eight incidents per boot, eight latch entries per helper and 16 KiB per incident are retained; the current boot is never pruned, even across clock corrections. Seven older boots are retained. There is no new dashboard/API status field.

## Inactive install, verification and activation

Use these steps only at the approved deployment stage, from the repository root. The isolated build/test does not authorize an install, a restart, a CAN request or fault injection.

1. Merge the reviewed code **without the separate activation commit**. With the van parked/asleep follow the [guarded broker restart procedure](../README.md#restarting-the-broker). Confirm this startup has no `usb-drop-recovery` line and (on first deployment) the record directory does not exist.
2. Run `projects/vehicle_data/usb_recovery_link/install.sh install` and `projects/vehicle_data/usb_recovery_link/install.sh status`. Status must verify the reviewed digest and installed owner/mode. Root runs only `/usr/local/sbin/vanpi-can-link-by-index`, not checkout code. Check the role link states and TX counters before and after the following operator checks; they must not change.
3. The live-namespace privilege check only lists authorization. Never send a privileged request in that namespace to a guessed unused index. Run the following from a shell as the service user; the first check must list the command as allowed. The second is **unprivileged** and must exit 3 with `errno=1 EPERM`.

   ```sh
   helper=/usr/local/sbin/vanpi-can-link-by-index
   deadline() { python3 -c 'import time; print(time.monotonic() + 2)'; }
   sudo -n -l -- /usr/bin/python3 -I -B "$helper" down 99999 --not-after "$(deadline)"
   /usr/bin/python3 -I -B "$helper" down 99999 --not-after "$(deadline)"
   ```

4. Test privileged acknowledgements **only in disposable network namespaces**, with no vehicle interface present. In order, expect exit 0 (namespace loopback), exit 3 `EOPNOTSUPP` (not CAN), exit 3 `ENODEV` (absent there).

   ```sh
   sudo -n unshare --net /usr/bin/python3 -I -B "$helper" down 1 --not-after "$(deadline)"
   sudo -n unshare --net /usr/bin/python3 -I -B "$helper" up-listen-only 1 500000 --not-after "$(deadline)"
   sudo -n unshare --net /usr/bin/python3 -I -B "$helper" down 7 --not-after "$(deadline)"
   ```

5. Only after review, successful inactive checks **and explicit owner acceptance of the bootstrap**, apply the separate `Activation:` unit change, install the tracked unit, reload systemd and run the guarded parked restart. Verify `systemctl show -p ExecStart van-telemetry.service` contains the flag and the journal for that startup says `usb-drop-recovery enabled`. A missing, improperly owned or changed helper disables recovery. The helpers and grant pipe protocol are unchanged. The installed state or a parked restart does not prove an armed mid-drive recovery. An optional physical unplug/replug test at idle with the vehicle parked and helpers armed requires separate owner authorization. `usbreset` does not reproduce a fresh enumeration.

## Rollback

1. Inspect every resolved channel with `python3 -m tools.can_operation_state status --channel <ch>` and inspect any `tmp/locks/operation-state/inhibit-nolock.*.json`. **Any active inhibit blocks a guarded restart**, including a fallback. Resolve its recorded condition under that operation's own inspection/end procedure. Do not end it merely to roll back or bypass the restart guard. An older CLI can list, honour and end the fallback by its own name.
2. Remove the activation flag, reinstall the unit, reload systemd and run the guarded parked restart. Confirm there is no enabled line for that startup. Recovery files are inert; preserve them.
3. For a code rollback, before reverting the source run `projects/vehicle_data/usb_recovery_link/install.sh uninstall`. Its `status` must now report absent. Then revert the code and perform the guarded parked restart. There is no need to restart unrelated services or delete audit records.
